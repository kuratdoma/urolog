# ADR 003: Data Layer Strictness (Pydantic & SQLAlchemy Sync)

## Status

Accepted (2026-02-25)

## Context

During the consolidation of the Patient Finance module, the system suffered recurrent `500 Internal Server Errors` on both API ingress (POST) and egress (GET). Upon investigation, this was traced back to weak structural coupling between the Pydantic schemas and the SQLAlchemy ORM models.

Specifically:

1. **Ingress (Payload to DB):** The frontend sent valid, UI-specific payload fields (`banka`, `notlar`, `adet`, `hizmet_adi`) that Pydantic accepted. When executing `**data.model_dump()` to instantiate a SQLAlchemy model (`FinansIslemSatir`), the ORM threw a `TypeError: invalid keyword argument` because those keys were not explicit database columns.
2. **Egress (DB to Payload):** Following successful generation, the API attempted to return a `FinansIslemResponse`. The Pydantic model (`from_attributes=True`) crashed for two reasons:
   - Missing native attributes on the ORM object (e.g., expecting `hizmet_adi`, but the column was `aciklama`).
   - `MissingGreenlet` errors due to lazy-loading deeply nested relationships (`satirlar`, `odemeler`, `taksitler`) in an `asyncpg` context.

## Decision: 2026 Edge-First Architecture Rules

To prevent this in future installations and feature deployments, the following architectural rules are now enforced system-wide:

### 1. Ingress Strictness (Safe Extraction)

Never blindly unpack Pydantic dumps (`**obj_in.model_dump()`) directly into SQLAlchemy constructors unless the Pydantic `Create` schema is strictly 1:1 with the database columns.
**Rule:** Use selective dictionary extraction or explicitly define assignments in mapping blocks.

```python
# Bad
row = FinansIslemSatir(**line_data) 

# Good (Enforced)
valid_satir = {
    "hizmet_id": line_data.get("hizmet_id"),
    "aciklama": line_data.get("hizmet_adi"), # Map UI to DB
    "miktar": line_data.get("adet", 1),
    "birim_fiyat": line_data.get("birim_fiyat"),
    "toplam_tutar": line_data.get("toplam")
}
row = FinansIslemSatir(**valid_satir)
```

### 2. Egress Strictness (Virtual Properties)

If a Pydantic `Response` schema expects a field that is heavily synthesized or mapped differently from the database column, enforce a `@property` on the SQLAlchemy model rather than attempting to compute it dynamically during dictionary transformation.

```python
class FinansIslemSatir(Base):
    aciklama = Column(String(255))
    
    @property
    def hizmet_adi(self) -> str:
        return self.aciklama or ""
```

### 3. Async Greenlet Safety

Whenever returning a Base Model that includes `List[Relation]`, the repository **must** explicitly query the transaction with deep eager-loading before returning. Do not rely on `session.refresh()` for multi-depth relations (`satirlar`, `odemeler.taksitler`).
**Rule:** Use `selectinload` for 1-to-N relationships to eliminate blocking sub-queries.

```python
# Enforced Retrieval
stmt = (
    select(FinansIslem)
    .options(
        selectinload(FinansIslem.satirlar),
        selectinload(FinansIslem.odemeler).selectinload(FinansOdeme.taksitler)
    )
    .where(FinansIslem.id == db_tx.id)
)
```

## Consequences

By making these three rules standard, we eliminate silent runtime type-mismatches and prevent database session lockups generated by asynchronous lazy-loads. Code reviews and future refactoring must enforce explicit, decoupled translation between what the Client sees (Pydantic) and what the Disk stores (SQLAlchemy).
